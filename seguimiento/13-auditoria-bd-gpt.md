## 2. Resumen

El modelo es compatible con FNBC bajo las dependencias funcionales documentadas; no se demuestra una violación de 1FN, 2FN, 3FN o FNBC.
No está listo para trasladarse sin aclaraciones a un contrato completo de persistencia: existen recorridos que permiten vender remesas vencidas o descontinuadas, desincronizar estado y existencias, y perder el bloqueo sanitario.
Faltan declaraciones inequívocas de nulabilidad, unicidad condicional y dominios; además, las correcciones de proveedor pueden romper la coherencia de las devoluciones.
El fundamento de DEC-022 requiere revisión técnica: un punto de guardado no permite continuar una transacción no confirmable con `XACT_ABORT ON`.
Se registran **23 hallazgos: 4 Bloqueantes, 4 Altos, 12 Medios y 3 Bajos**; los vacíos de negocio se mantienen como preguntas.

## 3. Estado por tabla

### 3.1. Claves, dependencias funcionales y formas normales

Se consideran candidatas únicamente las claves respaldadas por PK o por `UNIQUE` con componentes obligatorios. Para cada tabla, las dependencias enumeradas y las que se deducen de sus claves constituyen el conjunto documentado analizado; no se presume que sea una descripción exhaustiva de reglas de negocio todavía desconocidas.

**FNBC documental** significa que, para las dependencias no triviales identificadas, todo determinante es superclave. Implica 3FN, 2FN y 1FN. No certifica restricciones de dominio, transiciones de estado ni reglas entre tablas. No se concluye FNBC solo por tener un identificador artificial.

No se inventa un catálogo de principios activos ni una estructura de presentaciones mientras PEN-010 siga abierto (REG:53; DD:337–339).

### 3.2. Revisión de las 18 claves foráneas

`ND` significa nulabilidad **no declarada**, no autorización de `NULL`. La política general de DD:356 fija `ON DELETE NO ACTION` para todas las FKs salvo la excepción de DEC-006. No se detecta una omisión de esa política por no repetirse en cada fila. Las acciones `ON UPDATE` no se especifican; la propuesta para todas es `NO ACTION`, coherente con identificadores autogenerados y no editables. Esto no impide corregir un FK hacia otro padre existente.

### 4.1. Fundamento técnico externo y límites de la comprobación

Para **AUD-gpt-008**, Microsoft muestra una violación de FK con `XACT_ABORT ON` que deja la transacción no confirmable. Con `XACT_STATE() = -1` solo admite rollback completo; un retorno al punto de guardado y una actualización posterior no son válidos. El ejemplo de SAVE TRANSACTION comprueba ese estado antes de usar el savepoint. Estas reglas sustentan la contradicción técnica de DEC-022; no se ejecutó una reproducción sobre SQL Server local. [XACT_STATE](https://learn.microsoft.com/en-us/sql/t-sql/functions/xact-state-transact-sql?view=sql-server-ver17), [SAVE TRANSACTION](https://learn.microsoft.com/en-us/sql/t-sql/language-elements/save-transaction-transact-sql?view=sql-server-ver17).

Para **AUD-gpt-006**, un índice UNIQUE filtrado puede exigir unicidad únicamente a las filas Emitidas; no equivale a un UNIQUE de toda la columna `id_venta`. [CREATE INDEX, filtro y unicidad](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17).

Para **AUD-gpt-009/011**, CHECK rechaza FALSE, pero una expresión UNKNOWN por NULL puede aceptarse. De ahí que las propuestas separen NOT NULL de los controles de dominio y comprueben expresamente la presencia del comentario condicionado. Las restricciones UNIQUE ya generan su índice de soporte; no corresponde duplicarlo por defecto. [Restricciones UNIQUE y CHECK](https://learn.microsoft.com/en-us/sql/relational-databases/tables/unique-constraints-and-check-constraints?view=sql-server-ver17).

Para **AUD-gpt-021**, BIT almacena 0, 1 o NULL, y las cadenas TRUE/FALSE pueden convertirse; `DEFAULT (0)` evita trasladar una notación lógica ambigua al DDL. [BIT](https://learn.microsoft.com/en-us/sql/t-sql/data-types/bit-transact-sql?view=sql-server-ver17).

Las tablas siguen el prefijo `TBL_` en mayúsculas y las columnas snake_case; las PK/FK usan `id_` con el mismo nombre del identificador referenciado. No se halló una inconsistencia funcional por usar `id_detalle_dev` abreviado. El DDL todavía no define nombres físicos de restricciones; se recomienda aplicar una convención uniforme al escribirlo, sin presentar esa elección estética como una violación de normalización.
